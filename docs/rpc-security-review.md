# Atomic import RPC security review

The administrative draft depends on migrations 202611160001 through 202611160006. The corrected draft matches the versioned candidate `20261121235434_install_atomic_peoplepulse_import_rpc.sql`. Its embedded PostgreSQL test suite passed. Full-stack Supabase and hosted schema checks remain pending.

- The routine is `SECURITY INVOKER` with an empty search path. It requires a non-anonymous Auth identity with an unexpired JWT and company-wide import permission. Company authorization implies organization membership. Each dataset write remains subject to its own company and department RLS checks. The RPC accepts company-wide batches only, so department-only assignments fail closed.
- Each call accepts at most 5,000 rows and 8 MiB of combined UTF-8 PostgreSQL JSONB text for metadata and mapped rows. Containers at depth 5 are rejected. Rows must be objects with uniform keys from the dataset allowlist. Text length limits are 10 for dates, 80 for codes, 120 for specified categories, 160 for names and 250 for other row strings. Metadata and numeric payroll component keys have dedicated checks. SQL quotes allowlisted identifiers and binds the JSON payload.
- Company and source-batch IDs must match the request. Monthly rows must match the batch month. Employee references must be visible in the target company, with a same-batch reference allowance for Employee Master managers. Existing composite foreign keys and unique constraints enforce tenant integrity and exact database-key duplicate rejection. The browser adds normalized checks for visible records.
- The client derives a stable batch UUID from the staged payload. PostgreSQL independently binds it to a SHA-256 digest of the actor, scope, mapped rows and completeness metadata. File and sheet labels remain informational. Identical retries reuse the existing result, and a changed digest is rejected. Legacy Draft/Uploaded batches require administrator review. The routine never replaces existing rows.
- Draft creation, upload, row insertion, validation and audit events run in one transaction. The highest status this function writes is Validated. The role workflow and unpublished visibility remain enforced by the existing database policies and triggers. Execute is granted to authenticated accounts. Normal JWT signature validation happens at the Supabase API gateway, while the SQL checks expiration and identity claims from that gateway.
- The existing grants and RLS also support direct staging for callers with the required permissions. The browser submits solely through the RPC, and therefore fails closed when it is absent. RPC-specific checks and atomicity apply to the RPC path. Before confidential production use, decide whether to retire legacy direct staging and review the database privilege model. The current review UI exposes batch metadata and transitions. Independent inspection of unpublished mapped rows still needs a scoped review mechanism that preserves dashboard RLS.
- The 73-test RLS suite includes reviewer, approval and publication permission and actor checks. The 19-test RPC suite adds inputs, tenant checks, retry behavior, duplicates, unapproved visibility and transactional rollback. Both passed in disposable embedded PostgreSQL 18.7 with Auth fixtures. Full isolated Supabase execution is pending. JavaScript tests mock the transport and verify client behavior only.
